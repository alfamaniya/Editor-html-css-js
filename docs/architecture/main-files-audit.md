# گزارش معماری فایل‌های اصلی

- مخزن: [Editor-html-css-js](https://github.com/alfamaniya/Editor-html-css-js)
- شاخهٔ مبنا: `main`
- فایل‌های مرجع: `index.html`، `style.css` و `script.js`
- وضعیت: اندازه‌ها و SHAهای زیر از snapshot فعلی شاخه استخراج شده‌اند؛ پس از هر تغییر باید دوباره تولید شوند.

## وضعیت معماری واقعی

- صفحهٔ اصلی از سه textarea برای HTML، CSS و JavaScript استفاده می‌کند و کد اصلی آن در `script.js` است.
- CodeMirror و Monaco در صفحهٔ اصلی بارگذاری یا به چرخهٔ ویرایش متصل نیستند. pipeline بلااستفادهٔ CodeMirror حذف شده است؛ وابستگی یا خروجی بلااستفاده نباید دوباره به build افزوده شود.
- Visual Editor و قابلیت انتخاب المان حذف شده‌اند. پیش‌نمایش زندهٔ معمولی همچنان فعال و مستقل از ویرایش بصری است.
- فایل `index-test-etitor.html` خروجی تولیدی است؛ منبع توسعه نیست و در Git ignore می‌شود.
- `src/shared/validation/file-name.js` تنها منبع مقدار `EDITOR_FILE_NAME_MAX_LENGTH` است. مقدار فعلی 40 نویسه است و فرم، load، rename و backup/restore باید با آن هم‌خوان باشند.

## نقش فایل‌ها و مرزهای پیشنهادی

### index.html
ساختار و اتصال اجزای برنامه را نگه می‌دارد. شناسه‌های DOM و ترتیب بارگذاری اسکریپت‌ها قرارداد بین ماژول‌ها هستند؛ تغییر آن‌ها فقط همراه با اصلاح تمام مصرف‌کنندگان و build manifest مجاز است.

### style.css
قواعد عمومی Workspace، ویرایشگر و layout را نگه می‌دارد. CSS قابلیت‌های دارای فایل اختصاصی باید در همان پوشهٔ قابلیت نگهداری شود. قواعد responsive و divider باید در یک breakpoint منسجم تعریف شوند تا override متناقض ایجاد نشود.

### script.js
هستهٔ فعلی هنوز یک IIFE بزرگ است و بخش‌های متعددی را مدیریت می‌کند. انتقال آن باید تدریجی باشد:
1. پیش از جابه‌جایی، توابع، متغیرها، شناسه‌های DOM و listenerهای وابسته شناسایی شوند.
2. منطق داده از رندر DOM جدا شود.
3. هر قابلیت API محدود و قابل آزمون داشته باشد.
4. کد قدیمی فقط پس از انتقال موفق و تست رگرسیون حذف شود.

## ترتیب پیشنهادی توسعه

1. نگه‌داشتن تست‌های فعلی و اجرای آن‌ها در CI برای هر push و pull request.
2. جداسازی مدل فایل و ذخیره‌سازی از DOM در مرحله‌ای مستقل.
3. انتقال یک قابلیت در هر commit؛ اولویت با قابلیت‌هایی است که API و مرز روشن دارند.
4. افزودن تست برای هر قرارداد بین ماژول‌ها.
5. بازسازی standalone از روی manifest به‌روز و بررسی تطابق کامل منابع.
6. به‌روزرسانی README، این سند و درخت مخزن در هر تغییر ساختاری.

## دقت و محدودیت

این سند شرح معماری موجود در snapshot بالاست، نه ادعای تکمیل مهاجرت ماژولار. شماره خطوط و SHAها با هر تغییر فایل عوض می‌شوند. تست مرورگری و کارایی باید جدا از بررسی ایستای سورس انجام شوند.
