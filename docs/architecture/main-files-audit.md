# گزارش بررسی سه فایل اصلی پروژه

- مخزن: [Editor-html-css-js](https://github.com/alfamaniya/Editor-html-css-js)
- شاخه مبنا: `main`
- موضوع: بررسی `index.html`، `style.css` و `script.js` و تعیین عملیات پیشنهادی برای انتقال تدریجی به معماری ماژولار
- وضعیت: گزارش تحلیلی؛ عملیات ستون آخر پیشنهاد اجرایی است و به معنی انجام‌شدن تغییرات نیست.

> **اصل مهم معماری:** نسخه چندفایلی، سورس اصلی و مرجع توسعه است. فایل `editor v.html` خروجی بسته‌بندی‌شده برای ارسال ایمیلی و آزمایش در محیط شرکت است؛ نه سورس اصلی برنامه. ابزار `scripts/build-combined-editor.mjs` این خروجی را از سورس چندفایلی تولید می‌کند. تغییر قابلیت‌ها باید ابتدا در سورس چندفایلی انجام شود.

# ۴. ساختار معماری هدف پیشنهادی

این ساختار یک نقشه هدف است، نه ادعای اینکه تمام پوشه‌ها و فایل‌های آن هم‌اکنون پیاده‌سازی شده‌اند. نام و جایگاه نهایی هر ماژول باید با ساختار واقعی و وابستگی‌های آن تطبیق داده شود.

```text
src/
├── app/
│   └── app.js                  راه‌اندازی و هماهنگی قابلیت‌ها
├── shared/
│   ├── styles/                 توکن‌ها و استایل‌های مشترک
│   ├── utils/                  ابزارهای واقعاً مشترک
│   ├── dom/                    توابع عمومی DOM
│   ├── storage/                سرویس‌های مشترک ذخیره‌سازی
│   └── validation/             اعتبارسنجی‌های مشترک
└── features/
```

## اصول انتقال

1. در هر مرحله فقط یک قابلیت یا یک بخش با مرز روشن منتقل شود.
2. قبل از انتقال، تمام وابستگی‌های DOM، توابع، متغیرها و رویدادها شناسایی شوند.
3. تست‌های موجود پیش از تغییر اجرا شوند تا وضعیت پایه مشخص باشد.
4. HTML، CSS، JavaScript و تست‌های اختصاصی قابلیت تا حد امکان کنار هم نگهداری شوند.
5. کد فقط وقتی در `shared` قرار بگیرد که واقعاً بین چند قابلیت مشترک باشد.
6. پس از انتقال، رفتار قابلیت در مرورگر و با تست‌های مرتبط بررسی شود.
7. کد قدیمی پس از اطمینان از انتقال کامل حذف شود.
8. ترتیب بارگذاری و راه‌اندازی در یک نقطه مشخص مستند شود.
9. سورس چندفایلی مرجع باقی بماند و خروجی تک‌فایلی از روی آن ساخته شود.
10. پس از تغییر ساختار، README، درخت مخزن، ورودی‌های build و checkerها به‌روز شوند.

## ۶. اولویت‌های پیشنهادی

### اولویت اول: آماده‌سازی
- تهیه نقشه وابستگی‌های `script.js`
- شناسایی HTMLهای inline در `index.html`
- استخراج selectorهای تکراری و overrideها از `style.css`
- ثبت تست‌های موجود و وضعیت اجرای آن‌ها

### اولویت دوم: انتقال قابلیت‌ها
- انتخاب قابلیت‌های دارای مرز روشن مانند Word Tree یا Color Picker، پس از بررسی وابستگی واقعی
- جداسازی Preview و File Manager با حفظ قراردادهای ارتباطی
- انتقال تنظیمات و Backup/Restore با رعایت سازگاری داده‌های قبلی

### اولویت سوم: پاک‌سازی و تثبیت
- سبک‌سازی نهایی `index.html`
- حذف CSS و JavaScript قدیمی پس از انتقال موفق
- بازبینی کامل README و درخت فایل‌ها
- اعتبارسنجی build تک‌فایلی و زنجیره CI

## ۷. محدودیت و دقت گزارش

- محدوده خطوط مربوط به snapshot بررسی‌شده است؛ پس از تغییر فایل‌ها شماره خطوط جابه‌جا می‌شود.
- در اجرای واقعی، نام تابع، selector، شناسه DOM و وابستگی باید معیار دقیق باشد، نه شماره خط به‌تنهایی.
- این گزارش وضعیت ساختاری فایل‌ها را توصیف می‌کند و جایگزین بررسی خط‌به‌خط وابستگی‌ها در زمان هر انتقال نیست.
- پیشنهادهای ستون «عملیات پیشنهادی» برنامه کار آینده هستند و نباید به‌عنوان تغییرات انجام‌شده تلقی شوند.
- وجود پوشه رزروشده یا فایل `.gitkeep` به‌تنهایی به معنی پیاده‌سازی قابلیت نیست.
